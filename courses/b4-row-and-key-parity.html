Row and key parity

The first thing anyone checks after a load is the row count, and the first thing that lies is the row count. Tonight you check that the rows arrived the way a careful team does: counts first, then every key compared in both directions, then the copies per key, then the foreign keys that have to resolve on the other side. In DuckDB, on a small constructed pair where three faults are planted and the counts still agree.

Part 0

Where this session sits

Session 1 counted what Serai reads, session 2 put the moves in order and session 3 made the SQL mean the same thing on both engines. Now the first wave has loaded, and the question changes from "will it run" to "did every row arrive, once, and still join". That is rungs 0 and 1 of the ladder that Builder session 10's parity bench scores: row counts, then keys. The running case is a Constructed Serai Commerce example: tonight's twelve-order pair is constructed, and the bench numbers quoted on this page come from the same 8,614 real Olist orders, derived and masked, with each drift planted alone. Checks on real rows inside one system belong to the Testing Data and ML Code course's data checks session; this side owns parity between two systems that should hold the same rows.

Part 1 · covers row counts between two systems

One number per side

5 min live

A count is the cheapest comparison there is: one number from each warehouse. When the two differ, something is wrong, no argument. When they agree, almost nothing is proved.

LiveWhat a count can and cannot say3 min▶

On the bench, the late feed appends 367 orders a second time and the count moves from 8,614 to 8,981. That is the one defect a count is built for: rows added or lost. The other four defects change a value, a day or a join, and leave every row in place, so the count is exactly equal and rung 0 scores 1 of 5.

A count also cannot tell you which rows. Lose one order and duplicate another and the totals agree. The bench plants each drift alone, so it never shows two faults cancelling; real loads do, and tonight's build-along is built that way on purpose. Read an equal count as "not obviously broken", never as "the same".

Count resultWhat it provesWhat it does not prove
DifferentRows were added or lost on one sideWhich rows, or why
EqualNo net change in the number of rowsSame keys, same copies per key, same values
Self-studyCount the same thing on both sides3 min▶

Most count mismatches on a first run are definition mismatches, not load faults. The legacy count filters delivered orders and the new one does not; one side excludes soft-deleted rows; a test row lives only in the new warehouse; the window ends at midnight UTC on one side and local midnight on the other. Write the count as SQL with its filter and window, run the identical text on both sides, and put that text in the runbook beside the result.

Count per table first, then per partition you will reload by, usually a month. A per-month count tells you where the difference is, which matters when Builder session 6 reloads history one window at a time. Counting per day already starts the daily comparison that Builder session 5 runs on every metric.

Real world

Readiness is only as good as what the tests could see. TSB's own release on the independent review of its 2018 migration says go-live "followed a long period of testing, with reports to the Board signalling readiness", and that the review raised "questions around how testing was carried out". In December 2022 the Bank of England fined TSB "a total of £48,650,000" and found it "failed to organise and control the IT migration programme adequately." Nothing here says which checks TSB ran. The lesson is the general one: a green report is a statement about the checks under it, so write down what each check can and cannot see.

Part 2 · covers keys both ways, duplicates and foreign keys

Keys, compared in both directions

5 min live

A key comparison answers the questions a count cannot: which keys are missing in new, which are extra in new, and which arrived more than once. One full outer join on the key sorts every row into one of four buckets.

LiveFour buckets from one join3 min▶

Group each side by its key first, so each key carries its number of copies, then full outer join the two grouped sides on the key. A key with no partner in new is missing; a key with no partner in legacy is extra; a key on both sides with a different number of copies is duplicated (or deduplicated, if legacy had the copies). Everything else is matched.

"Both directions" is the part people skip. A LEFT JOIN from legacy to new finds the missing keys and is blind to extras; a test row, a replayed batch or a stray partition only shows up from the other side. On the bench the late feed is the duplicated bucket: 367 duplicated keys, which is exactly the 8,981 minus 8,614 that the count saw, now with names attached.

LiveThe keys you join on, not just the key you load3 min▶

The case-sensitive drift adds no row and loses no row. Every order key matches. What breaks is the customer key: Export C writes its keys in lower case, the new warehouse joins case-sensitively, and on the bench 1,767 customer keys no longer resolve in new against 0 in legacy. No count and no order-key diff can see it. A foreign-key check can: for each side, count the rows whose customer key finds no customer.

Run it on both sides and compare, never on new alone. A legacy that already had unresolved keys is a fact to record, not a migration fault; the fault is the difference. This is the check that proves rule R4 from Builder session 3 held on real rows.

Self-studyWhen a table has no key3 min▶

AWS's Database Migration Service documentation, a vendor claim about its own product, says its validation "compares each row in the source with its corresponding row at the target, verifies the rows contain the same data, and reports any mismatches", and that "Data validation requires that the table has a primary key or unique index." Any key comparison has the same requirement. Event logs, append-only facts and old reporting extracts often have none.

Three honest options, in order of preference: find the natural key the business uses (order id plus line number), declare a composite key and first prove it is unique on legacy, or fall back to comparing aggregates per partition and write down that this table has no key-level check. Never invent a key from a row number: two loads number the same rows differently.

Real world

Two copies, different writes. GitHub's analysis of its 21 October 2018 incident describes connectivity "restored in 43 seconds", after which a database "contained writes that were not present in the other data center". The site ran with "degraded service for 24 hours and 11 minutes", and the team chose to "prioritize data integrity over site usability and time to recovery". A count would have said the two sides were close. Only a comparison by key says which rows each side holds.

Part 3 · covers what keys cannot see

Same keys, different numbers

5 min live

Rung 1 is clean when every key is present once on each side and every foreign key resolves. Three of the bench's five defects pass that test with every key intact, because they change a value or a day, not a row.

LiveThree defects that keep every key3 min▶

The fixed -03:00 offset moves 72 orders to the day before; their keys are untouched. The missing review loaded as 0 turns 68 NULLs into zeros; same 8,614 orders. Integer division changes a metric, items per order, from 1.1427 to 1, without touching a row. All three sail through counts and keys, which is why rung 1 scores 2 of 5 with 3 missed, and why the suite cannot stop here.

Builder session 5 climbs the next rung: six metrics compared every day, exactly, then at the monthly grain against Serai's signed bar. Keep tonight's report anyway. When an aggregate moves, the key report tells you in seconds whether rows are the reason.

Self-studyComparing values per key: row hashing4 min▶

Between keys and aggregates sits a third option: hash each row's values on both sides and compare the hashes per key. Google's open-source Data Validation Tool lists row validation with SHA256 hashing beside column validation (count, sum, avg, min, max, stddev, group by), schema validation and custom-query validation. reladiff describes itself as "a fork of an archived project called data-diff" that uses "a divide-and-conquer algorithm, based on matching hashes, to efficiently identify modified segments"; the original data-diff repository was archived in May 2024. These are tool descriptions, fast-moving; re-verify before you rely on one.

Whether row hashing or aggregates is "enough" is genuinely contested. A hash finds the one changed row an aggregate can average away, and it needs a key and a careful definition of each value, because an exact hash also flags differences you have agreed to accept, such as floating-point sums, unless you round before hashing. Aggregates need no key and compare at the grain people read, and can let a single row slip. Which cost is worse, a missed row or a pile of alarms, is a business call for the bar's signer, not a tool setting.

Real world

The validation tools offer both, side by side. AWS DMS goes row by row and needs a key; Google's Data Validation Tool offers column aggregates and row hashes side by side. Read both as vendor claims about their own products. Neither decides which differences block a cutover. The tool reports differences; a person signs which ones matter, and that signature is runbook section 4.

Build-along

Plant three faults, then find them

★ 22 min · everyone builds

You need DuckDB: pip install duckdb and a Python prompt, or the DuckDB command-line shell. Constructed Serai Commerce example: twelve orders in legacy, extending the six from Builder session 3's export, and a new side with three planted faults. Paste the setup once, then run the queries in order. Every output below is what DuckDB 1.5.3 printed on this exact pair.

Load the constructed pair. Legacy has twelve orders, each once, with customer keys stored in upper case. New has the same orders with three faults planted: o9 never arrived, o12 was appended twice by a late feed, and o3 and o5 kept the lower-case customer keys their marketplace export writes.

★ Setup (paste once)CREATE OR REPLACE TABLE customers AS SELECT * FROM (VALUES ('C1A7'),('B22F'),('9E0D'),('4F11'),('A3C2'),('7D90')) c(customer_key); CREATE OR REPLACE TABLE legacy_orders AS SELECT order_id, customer_key, CAST(order_day AS DATE) AS order_day, item_value FROM (VALUES ('o1','C1A7','2017-01-15',120.50),('o2','B22F','2017-01-15', 59.90), ('o3','C1A7','2017-01-15', 35.00),('o4','9E0D','2017-07-09',210.00), ('o5','B22F','2017-07-10', 44.00),('o6','9E0D','2017-07-11', 18.00), ('o7','4F11','2017-07-11', 72.40),('o8','A3C2','2017-07-12', 99.00), ('o9','7D90','2017-07-12', 15.50),('o10','4F11','2017-07-13', 64.00), ('o11','A3C2','2017-07-13', 28.90),('o12','7D90','2017-07-14',130.00) ) t(order_id, customer_key, order_day, item_value); CREATE OR REPLACE TABLE new_orders AS SELECT order_id, customer_key, CAST(order_day AS DATE) AS order_day, item_value FROM (VALUES ('o1','C1A7','2017-01-15',120.50),('o2','B22F','2017-01-15', 59.90), ('o3','c1a7','2017-01-15', 35.00),('o4','9E0D','2017-07-09',210.00), ('o5','b22f','2017-07-10', 44.00),('o6','9E0D','2017-07-11', 18.00), ('o7','4F11','2017-07-11', 72.40),('o8','A3C2','2017-07-12', 99.00), ('o10','4F11','2017-07-13', 64.00),('o11','A3C2','2017-07-13', 28.90), ('o12','7D90','2017-07-14',130.00),('o12','7D90','2017-07-14',130.00) ) t(order_id, customer_key, order_day, item_value);

Q1, rung 0: one count per side. Twelve and twelve. If this were the whole suite, the load would be signed off tonight.

★ Q1 · row countsSELECT (SELECT count(*) FROM legacy_orders) AS legacy_rows, (SELECT count(*) FROM new_orders) AS new_rows; -- legacy_rows 12 | new_rows 12

Q2, keys both ways. Group each side by key so every key carries its copies, then full outer join. o9 is missing in new, o12 is duplicated, no key is extra, and ten keys match.

★ Q2 · four bucketsWITH l AS (SELECT order_id, count(*) AS n FROM legacy_orders GROUP BY order_id), r AS (SELECT order_id, count(*) AS n FROM new_orders GROUP BY order_id) SELECT CASE WHEN r.order_id IS NULL THEN 'legacy only' WHEN l.order_id IS NULL THEN 'new only' WHEN l.n <> r.n THEN 'duplicated' ELSE 'matched' END AS bucket, count(*) AS order_keys, string_agg(coalesce(l.order_id, r.order_id), ', ' ORDER BY coalesce(l.order_id, r.order_id)) AS which FROM l FULL OUTER JOIN r ON l.order_id = r.order_id GROUP BY bucket ORDER BY bucket; -- duplicated | 1 | o12 -- legacy only | 1 | o9 -- matched | 10 | o1, o10, o11, o2, o3, o4, o5, o6, o7, o8

Q3, the duplicates by name. On a real table this list is what you hand the reload owner: which keys, how many copies. On the bench it is 367 keys long.

★ Q3 · keys with more than one copySELECT order_id, count(*) AS copies FROM new_orders GROUP BY order_id HAVING count(*) > 1; -- o12 | 2

Q4, customer keys on both sides. Every order key matched in Q2 for o3 and o5, and still their customers do not resolve in new. Run the same check on legacy, then list the new rows and test whether upper case would resolve them.

★ Q4 · unresolved foreign keysSELECT 'legacy' AS side, count(*) FILTER (WHERE c.customer_key IS NULL) AS unresolved FROM legacy_orders o LEFT JOIN customers c ON c.customer_key = o.customer_key UNION ALL SELECT 'new', count(*) FILTER (WHERE c.customer_key IS NULL) FROM new_orders o LEFT JOIN customers c ON c.customer_key = o.customer_key; -- legacy | 0 -- new | 2 SELECT o.order_id, o.customer_key, upper(o.customer_key) IN (SELECT customer_key FROM customers) AS resolves_if_upper FROM new_orders o LEFT JOIN customers c ON c.customer_key = o.customer_key WHERE c.customer_key IS NULL ORDER BY o.order_id; -- o3 | c1a7 | true -- o5 | b22f | true

Q5, one report row: runbook section 4, rungs 0 and 1. Every number side by side, so nobody has to read four outputs to know whether the table passed. A clean table prints equal rows, zeros for missing and extra, and the same duplicated and unresolved numbers on both sides.

★ Q5 · the key report rowWITH l AS (SELECT order_id, count(*) AS n FROM legacy_orders GROUP BY order_id), r AS (SELECT order_id, count(*) AS n FROM new_orders GROUP BY order_id), u AS (SELECT 'legacy' AS side, o.customer_key FROM legacy_orders o LEFT JOIN customers c USING (customer_key) WHERE c.customer_key IS NULL UNION ALL SELECT 'new', o.customer_key FROM new_orders o LEFT JOIN customers c USING (customer_key) WHERE c.customer_key IS NULL) SELECT (SELECT sum(n) FROM l) AS legacy_rows, (SELECT sum(n) FROM r) AS new_rows, count(*) FILTER (WHERE r.order_id IS NULL) AS missing_keys, count(*) FILTER (WHERE l.order_id IS NULL) AS extra_keys, count(*) FILTER (WHERE l.n > 1) AS dup_legacy, count(*) FILTER (WHERE r.n > 1) AS dup_new, (SELECT count(*) FROM u WHERE side = 'legacy') AS unresolved_legacy, (SELECT count(*) FROM u WHERE side = 'new') AS unresolved_new FROM l FULL OUTER JOIN r ON l.order_id = r.order_id; -- legacy_rows 12 | new_rows 12 | missing_keys 1 | extra_keys 0 -- dup_legacy 0 | dup_new 1 | unresolved_legacy 0 | unresolved_new 2

The count agreed because two faults cancelled. One key lost and one key doubled leave twelve rows on each side. The bench plants every drift alone, so it never shows this; a real load can carry several faults at once, which is the strongest reason the suite never stops at rung 0. Also note what Q5 did not flag: o1's day and o3's review are identical here because nothing was planted in them. Builder session 5 plants that kind of drift and compares values.

Check yourself

Three questions

Clear all three and Builder session 4 gets stamped in your passport.

1 · Tonight's pair shows 12 rows on each side. What does the equal count prove?

o9 went missing and o12 arrived twice, so the totals agree. A count proves a difference when it differs and almost nothing when it agrees.

2 · On the bench, the case-sensitive join adds no row and loses no row. How does rung 1 still catch it?

Every order key matches. The fault is in the keys you join on, so the check resolves customer keys on each side and compares the two numbers.

3 · Which planted defect passes both rung 0 and rung 1?

Rung 1 catches 2 of 5, the late rows and the case-sensitive join. The review-as-0 drift, the fixed offset and integer division keep every key and change a value, a day or a metric.
