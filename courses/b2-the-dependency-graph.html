The dependency graph and the order of moves

Session 1 gave you eleven lineage edges and a status for every table. Tonight those edges become a plan. A table can only be proved in the new warehouse once everything it is built from is there and proved, so the order of moves is not a preference: it falls out of the graph. You will find the sources and sinks, write a recursive query that gives every table its wave, guard it against cycles, take the retirements out first, and check that no edge points backwards. Part 1 · covers nodes, edges, sources and sinks

Read the edges as a graph

5 min live

An edge list is already a graph. Every table is a node; every "read A, write B" query is an edge from A to B. Two counts per node, edges in and edges out, sort every table into a source, a sink or something in between, and that sorting is the first fact a move plan needs.

LiveSources, sinks, and why direction matters3 min▶

A source has no edge coming in: nothing inside the warehouse builds it, so it is loaded from outside, here the three marketplace exports, the review feed and a reference table of states and regions. A sink has no edge going out: nothing inside the warehouse is built from it, so its only consumers are people and dashboards, or nobody. Everything else is in the middle.

RoleSerai's tablesWhat it means for the move
Source3 exports, raw.reviews, ref.state_regionCan move first: it needs nothing else in the new warehouse to be built
Middlestg.orders, stg.reviews, mart.orders_dailyMoves after its inputs, before its outputs
Sinkorders_monthly, brand_review, both scorecardsMoves last, and is where people notice a wrong number

Direction is the whole point. stg.orders is fed by three edges and feeds four. Move it before the exports and the new warehouse has nothing to build it from; move it after the marts and the marts have nothing to read.

Self-studyThe two tables with no edge at all2 min▶

mart.region_sales_2019 and tmp.orders_backup_2017 appear in the table list but in no edge: no query in the log both read one table and wrote another while touching them. A query that only reads a table produces no edge, which is why a node list built from edges alone has 12 tables, not 14. Always start the plan from the full table list, the same lesson as session 1's Q2, or the isolated tables silently drop out of the plan instead of being decided.

Isolated tables are often exactly the retire candidates. Both of these are. When an isolated table is read by people, it can move in any wave, because nothing depends on it and it depends on nothing in the warehouse.

Real world

A phased move means two warehouses running side by side for a while. Google Cloud's 2019 migration blog describes an iterative move in which "both your data warehouse and BigQuery can be actively used in parallel". Read it as a vendor claim about its own process. The graph is what makes that safe or unsafe: a table moved before its inputs has to be fed across systems, and every cross-system feed is one more thing to build, watch and later switch off.

Part 2 · covers depth by recursive walk and cycle detection

A wave is the longest path from a source

5 min live

Give every source depth 0. Walk each edge forward, adding 1. A table reachable by several paths keeps its deepest one, and that number is its wave: the earliest point at which every table it reads from has already moved.

LiveHow a recursive CTE walks a graph4 min▶

WITH RECURSIVE has two halves joined by UNION ALL. The anchor runs once and produces the starting rows: every source at depth 0, with a path holding just itself. The recursive half runs again and again, each time on only the rows the previous iteration produced, joining them to the edges and stepping one table forward. When an iteration produces no rows, the query stops and returns everything it collected.

On Serai's graph that is four productive iterations: 5, 5, 13 and 3 rows, 26 in all. Then GROUP BY table_name with max(depth) folds the paths back into one row per table. The walk carries the path as a list so you can see how it got there; that list also powers the cycle guard.

LiveWhy the deepest path, not the shortest2 min▶

mart.brand_review reads ref.state_region, a source, so one path reaches it at depth 1. It also reads stg.orders and stg.reviews, which are themselves at depth 1, so other paths reach it at depth 2. Take the shortest and brand_review lands in wave 1, alongside the staging tables it reads. You would be proving a mart against inputs that have not been proved yet, and any difference could come from either. Take the deepest and it waits for wave 2, when everything under it is settled.

Self-studyCycles, and what a cycle tells you3 min▶

A cycle is a chain of edges that comes back to where it started: a monthly mart that writes a correction back into staging, say. A graph with a cycle has no valid order, because every table in the loop is waiting for another one. A recursive walk on a cycle never runs out of rows on its own. Two guards stop it: skip any target already in the current path, and cap the depth at a number far larger than any real chain. The build-along plants one bad edge and shows the guard catching it.

When you find a real cycle, the query cannot fix it. Someone has to decide which edge is the feedback, often a correction or a snapshot, and move that part of the loop as one unit or break the loop for the duration of the move. Write the decision into the runbook.

On a large estate, the number of paths can grow quickly, because every route to a table is a separate row. If the walk gets slow, the same waves come from repeatedly peeling off the tables with no remaining inputs, a method known as Kahn's algorithm; it reaches the same answer with one pass per wave.

Real world

Change goes out in a defined order. Google's SRE book says "Almost all updates to Google's services proceed gradually, according to a defined process". That chapter is about releasing software, not moving data, so it is an analogy, not evidence about warehouses. The habit carries across: the order is written down before the change starts, so that nobody chooses the next step under pressure, and a wave plan computed from the graph is that written order for a migration.

Part 3 · covers retirements first and waves proved in order

Retire first, then move in waves

5 min live

Take the three retire candidates out of the graph before you compute the waves. Then move wave 0, prove it, and only then start wave 1. The plan is short because the graph is honest.

LiveWhy retirements go first3 min▶

Leave mart.seller_scorecard_v1 in the graph and the walk puts it in wave 2 with four tables instead of three: one more table to translate in session 3, reload in session 6 and prove in sessions 4 and 5, for a mart nobody reads. Take it out first and wave 2 shrinks. The other two retire candidates have no edges, so removing them changes no wave, but it does remove them from every later checklist.

Retiring first does not mean dropping first. Use the two steps from session 1: stop writing and revoke reads with a date announced, then archive and drop after a quiet period. The first step is enough to take a table out of the move.

LiveEach wave proved before the next2 min▶

A wave is done when its tables are loaded in the new warehouse and pass the parity checks you build in sessions 4 and 5 against the legacy copies. Only then does the next wave start reading them. If wave 1 fails parity, the fault is in wave 1's two tables, because wave 0 already passed. Prove all eleven at the end instead and every difference could have come from anywhere upstream.

Waves set the order, not the calendar. How long each wave runs in parallel with legacy, and how long the whole parallel run lasts, is contested: no source gives a number. Session 7 takes that up; Serai's four weeks there is constructed.

Self-studyWaves or one switch: a real disagreement3 min▶

A wave plan is a phased move. The alternative is a single switch: build everything in the new warehouse, prove it as a whole, and move every reader on one day. The vendor guides recommend iterating; the case for one switch is that it avoids months of two systems feeding each other. The Bank of England fined TSB "a total of £48,650,000" in 2022 and found it "failed to organise and control the IT migration programme adequately", after a single large switch in 2018. One case is not a base rate, and nobody has published how often either approach fails. Even if your team chooses one switch, the waves still tell you the order to build and prove in before the day comes.

Real world

Done is checked per iteration. Google Cloud's 2019 migration blog says: "At the end of each iteration, validate that the use case was successfully migrated according to your definition of done." Read it as a vendor claim. A wave with a proof gate is that sentence turned into a schedule, and the definition of done is the one the leader track signs in Leader session 1.

Two graphs, two owners. The orchestrator's DAG decides when jobs run each night; the dependency graph on this page decides the order tables move once. They are built from the same edges and answer different questions. Scheduling DAGs belong to the Data Orchestration course, session 2; this page owns only the order of moves.

Build-along

Six queries, one order of moves

★ 22 min · everyone builds

You need DuckDB: pip install duckdb and a Python prompt, or the DuckDB command-line shell. Paste the setup once, then run the six queries in order. Every output below is what DuckDB printed on this exact graph.

Load the graph. The 11 edges are exactly what session 1's Q3 returns on the constructed log; if you still have that session open, CREATE TABLE edges AS its Q3 gives the same rows. The retire table holds session 1's three retire candidates.

★ Setup (paste once)CREATE OR REPLACE TABLE edges AS SELECT * FROM (VALUES ('raw.orders_export_a','stg.orders'), ('raw.orders_export_b','stg.orders'), ('raw.orders_export_c','stg.orders'), ('raw.reviews','stg.reviews'), ('stg.orders','mart.orders_daily'), ('mart.orders_daily','mart.orders_monthly'), ('stg.orders','mart.brand_review'), ('stg.reviews','mart.brand_review'), ('ref.state_region','mart.brand_review'), ('stg.orders','mart.seller_scorecard_v2'), ('stg.orders','mart.seller_scorecard_v1') ) e(source, target); CREATE OR REPLACE TABLE retire AS SELECT * FROM (VALUES ('mart.seller_scorecard_v1'),('mart.region_sales_2019'),('tmp.orders_backup_2017') ) r(table_name);

Q1, sources, middles and sinks. Count edges in and out for every node. Twelve rows: five sources, three in the middle, four sinks.

★ Q1 · rolesWITH nodes AS (SELECT source AS n FROM edges UNION SELECT target FROM edges) SELECT n AS table_name, (SELECT count(*) FROM edges WHERE target = n) AS fed_by, (SELECT count(*) FROM edges WHERE source = n) AS feeds, CASE WHEN (SELECT count(*) FROM edges WHERE target = n) = 0 THEN 'source' WHEN (SELECT count(*) FROM edges WHERE source = n) = 0 THEN 'sink' ELSE 'middle' END AS role FROM nodes ORDER BY role DESC, table_name; -- source: the 3 exports, raw.reviews, ref.state_region (fed_by 0, feeds 1) -- sink: mart.brand_review 3 | 0, orders_monthly 1 | 0, scorecard_v1 1 | 0, scorecard_v2 1 | 0 -- middle: mart.orders_daily 1 | 1, stg.orders 3 | 4, stg.reviews 1 | 1 (12 rows)

Q2, the wave of every table. The anchor picks the sources; the recursive half steps one edge forward and refuses to revisit a table already in the path. paths_seen shows how many routes reach each table.

★ Q2 · recursive walkWITH RECURSIVE walk(table_name, depth, path) AS ( SELECT source, 0, [source] FROM edges WHERE source NOT IN (SELECT target FROM edges) UNION ALL SELECT e.target, w.depth + 1, list_append(w.path, e.target) FROM walk w JOIN edges e ON e.source = w.table_name WHERE NOT list_contains(w.path, e.target) AND w.depth < 20 ) SELECT table_name, max(depth) AS wave, count(*) AS paths_seen FROM walk GROUP BY table_name ORDER BY wave, table_name; -- wave 0: the 5 sources, 1 path each -- wave 1: stg.orders 3, stg.reviews 1 -- wave 2: mart.brand_review 5, orders_daily 3, scorecard_v1 3, scorecard_v2 3 -- wave 3: mart.orders_monthly 3 (12 rows)

Q3, why the maximum. List every path that reaches mart.brand_review. One reaches it at depth 1; four at depth 2. The maximum is the wave.

★ Q3 · every path to one tableWITH RECURSIVE walk(table_name, depth, path) AS ( SELECT source, 0, [source] FROM edges WHERE source NOT IN (SELECT target FROM edges) UNION ALL SELECT e.target, w.depth + 1, list_append(w.path, e.target) FROM walk w JOIN edges e ON e.source = w.table_name WHERE NOT list_contains(w.path, e.target) AND w.depth < 20 ) SELECT depth, array_to_string(path, ' > ') AS path FROM walk WHERE table_name = 'mart.brand_review' ORDER BY depth, path; -- 1 | ref.state_region > mart.brand_review -- 2 | raw.orders_export_a > stg.orders > mart.brand_review -- 2 | raw.orders_export_b > stg.orders > mart.brand_review -- 2 | raw.orders_export_c > stg.orders > mart.brand_review -- 2 | raw.reviews > stg.reviews > mart.brand_review

Q4, the cycle guard catching a bad edge. Plant a constructed edge from the monthly mart back into staging, walk again with a cycle flag that marks a step onto a table already in the path, and list the loops. Then delete the bad edge.

★ Q4 · plant, detect, removeINSERT INTO edges VALUES ('mart.orders_monthly', 'stg.orders'); WITH RECURSIVE walk(table_name, depth, path, cycle) AS ( SELECT source, 0, [source], false FROM edges WHERE source NOT IN (SELECT target FROM edges) UNION ALL SELECT e.target, w.depth + 1, list_append(w.path, e.target), list_contains(w.path, e.target) FROM walk w JOIN edges e ON e.source = w.table_name WHERE NOT w.cycle AND w.depth < 20 ) SELECT array_to_string(path, ' > ') AS cycle_path FROM walk WHERE cycle ORDER BY cycle_path; -- raw.orders_export_a > stg.orders > mart.orders_daily > mart.orders_monthly > stg.orders -- raw.orders_export_b > stg.orders > mart.orders_daily > mart.orders_monthly > stg.orders -- raw.orders_export_c > stg.orders > mart.orders_daily > mart.orders_monthly > stg.orders DELETE FROM edges WHERE source = 'mart.orders_monthly' AND target = 'stg.orders';

Q5, retire first, then the waves. Drop every edge that touches a retire candidate, walk what is left, and roll the result up. This is runbook section 2.

★ Q5 · the order of movesWITH RECURSIVE live AS ( SELECT * FROM edges WHERE source NOT IN (SELECT table_name FROM retire) AND target NOT IN (SELECT table_name FROM retire) ), walk(table_name, depth, path) AS ( SELECT source, 0, [source] FROM live WHERE source NOT IN (SELECT target FROM live) UNION ALL SELECT e.target, w.depth + 1, list_append(w.path, e.target) FROM walk w JOIN live e ON e.source = w.table_name WHERE NOT list_contains(w.path, e.target) AND w.depth < 20 ), waves AS (SELECT table_name, max(depth) AS wave FROM walk GROUP BY table_name), plan AS ( SELECT 'retire first' AS step, count(*) AS tables, string_agg(table_name, ', ' ORDER BY table_name) AS which FROM retire UNION ALL SELECT 'wave ' || wave, count(*), string_agg(table_name, ', ' ORDER BY table_name) FROM waves GROUP BY wave ) SELECT * FROM plan ORDER BY step <> 'retire first', step; -- retire first | 3 | mart.region_sales_2019, mart.seller_scorecard_v1, tmp.orders_backup_2017 -- wave 0 | 5 | raw.orders_export_a, raw.orders_export_b, raw.orders_export_c, raw.reviews, ref.state_region -- wave 1 | 2 | stg.orders, stg.reviews -- wave 2 | 3 | mart.brand_review, mart.orders_daily, mart.seller_scorecard_v2 -- wave 3 | 1 | mart.orders_monthly

Q6, check the order. Join every edge to the waves at both ends. A correct plan has every edge going from a lower wave to a higher one; a single backward or flat edge means something moves before its input.

★ Q6 · no edge points backwardsWITH RECURSIVE walk(table_name, depth, path) AS ( SELECT source, 0, [source] FROM edges WHERE source NOT IN (SELECT target FROM edges) UNION ALL SELECT e.target, w.depth + 1, list_append(w.path, e.target) FROM walk w JOIN edges e ON e.source = w.table_name WHERE NOT list_contains(w.path, e.target) AND w.depth < 20 ), waves AS (SELECT table_name, max(depth) AS wave FROM walk GROUP BY table_name) SELECT count(*) AS edges, count(*) FILTER (WHERE s.wave < t.wave) AS forward, count(*) FILTER (WHERE s.wave >= t.wave) AS backward_or_flat FROM edges e JOIN waves s ON s.table_name = e.source JOIN waves t ON t.table_name = e.target; -- edges 11 | forward 11 | backward_or_flat 0

Note the ORDER BY in Q5. DuckDB refused ORDER BY step <> 'retire first', step written directly after a UNION ALL, because an expression there must appear in the select list. Wrapping the union in a CTE named plan and sorting the outer SELECT fixes it. The binder error is worth seeing once; other engines may phrase or enforce the rule differently, so check yours.

Check yourself

Three questions

Clear all three and Builder session 2 gets stamped in your passport.

1 · mart.brand_review is reached at depth 1 through ref.state_region and at depth 2 through both staging tables. Which wave does it belong in?

A wave is the longest path from a source. With the shortest path, brand_review would move alongside the staging tables it reads, and a difference in it could come from either side.

2 · What does NOT list_contains(w.path, e.target) do in the recursive half of Q2?

The path list is the walk's memory of where it has been. Together with the depth cap it guards against cycles; Q4 flips the same test into a flag so the loop is reported instead of silently cut.

3 · Why take mart.seller_scorecard_v1 out of the graph before computing the waves?

Every retirement shrinks every later step. scorecard_v1 is a sink with no reader, so removing it changes no other table's wave and saves its whole share of the work.
