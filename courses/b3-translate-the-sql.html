Part 0

Where this session sits

Session 1 counted what Serai reads; session 2 put the moves in order. Before the first wave can move, the SQL that builds each table has to run on the new warehouse and give the same answer. That is the job tonight, and it is narrower than it sounds: not rewriting for speed, not redesigning a model, only making sure the translated text means what the old text meant. The running case is a Constructed Serai Commerce example: a six-order export small enough to read row by row, built so each dialect gap fires once. Changing a schema inside one database, and the migration tools that run in CI/CD, belong to the DataOps course's session on database migrations; this side owns moving SQL from one engine to another.

Part 1 · covers division, rounding and float against DECIMAL

Numbers that quietly change type

5 min live

The most common translation defect is arithmetic that looks identical on both sides. Two whole numbers divided give a fraction on one engine and a whole number on another, and money held as floating point stops adding up to the cent.

LiveInteger division: same text, different answer3 min▶

The PostgreSQL documentation says integer division "truncates the result towards zero", so 5 / 2 is 2. DuckDB's documentation says the opposite for the same operator: "When both operands are integers, / performs floating points division (5 / 2 = 2.5)", and "// performs integer division (5 // 2 = 2)". Neither is wrong. A query moved between two engines with different defaults still compiles, and answers a different question. Run both operators, and a negative case, since truncation towards zero and rounding down part company below zero:

★ Run bothSELECT 5 / 2 AS slash, 5 // 2 AS double_slash, -7 // 2 AS neg; -- slash 2.5 | double_slash 2 | neg -3

In the DuckDB build used for this page (1.5.3), -7 // 2 printed -3, so // truncated towards zero here too. The translation rule does not depend on remembering which engine does what: cast one side to DECIMAL before you divide, and round to a stated precision at the end. The intent is then in the text, not in a default.

Self-studyFloat, DECIMAL and rounding halves4 min▶

Two of the bench's seven drifts are accepted differences, and both are arithmetic. Money summed as floating point differs from the same money summed in exact cents in the last bits; freight split across order lines and rounded per line can lose or gain a cent per order. Run the three cases from the figure:

★ Float against DECIMAL, and a per-line splitSELECT 0.1::DOUBLE + 0.2::DOUBLE AS dbl, 0.1::DECIMAL(4,2) + 0.2::DECIMAL(4,2) AS dec; -- dbl 0.30000000000000004 | dec 0.30 SELECT round(10.00 / 3, 2) AS per_line, 3 * round(10.00 / 3, 2) AS three_lines; -- per_line 3.33 | three_lines 9.99 SELECT round(2.5) AS half, round(0.125::DECIMAL(6,3), 2) AS dec_half; -- half 3 | dec_half 0.13

Two things to note from the outputs. First, the per-line columns came back typed double: in the build we ran, dividing a DECIMAL by an integer returned a DOUBLE, so the rule rounds explicitly at the end rather than trusting the type to carry cents. Second, halves: DuckDB printed 3 for round(2.5). Do not assume the legacy engine rounds a half the same way; run the same literals on both engines and write down what each prints.

On the bench, floating-point money differs on 302 days of item value and 269 days of freight, by about 2e-10 BRL in the worst month, and the per-line split moves total freight from BRL 195,579.02 to BRL 195,579.59. Exact equality on every day flags both. Builder session 5 shows why a signed tolerance clears them while still catching the real defects.

Real world

Two engines document opposite answers to 5 / 2. PostgreSQL's mathematical operators page gives 5 / 2 as 2, because integer division "truncates the result towards zero". DuckDB's numeric functions page gives the same expression as 2.5 and moves integer division to //. Both pages are clear and both engines behave as documented. The defect only appears in the gap between them, which is exactly where a migration lives.

Part 2 · covers NULL, empty strings and zero

NULL, empty and zero are three different answers

5 min live

A missing review score is a NULL in the legacy warehouse. The export writes it as an empty string, and the new loader has to decide what an empty string means. Pick zero and the average review score drops while every count still looks fine.

Live= NULL is never true2 min▶

The PostgreSQL documentation puts it plainly: "Do not write expression = NULL because NULL is not 'equal to' NULL". It offers IS DISTINCT FROM, which it describes as "Not equal, treating null as a comparable value". Translated code that compares nullable columns with = or <> loses rows silently, most often in a join or an anti-join that builds a change list.

★ Three-valued logic in one lineSELECT NULL = NULL AS eq, NULL IS DISTINCT FROM NULL AS distinct_nulls, '' IS NULL AS empty_is_null; -- eq NULL | distinct_nulls false | empty_is_null false

The first column is not false, it is NULL, and a WHERE clause keeps only rows where the condition is true. The last column is the start of the next card: in DuckDB, an empty string is a value, not a NULL.

LiveEmpty string, NULL and zero in a CAST3 min▶

Text exports have no NULL, only an empty field. Whatever the loader does with that empty field becomes the new warehouse's truth. A plain CAST('' AS INTEGER) in DuckDB refuses: it printed Conversion Error: Could not convert string '' to INT32. That error is a gift, because it stops the load. The defect comes from the "fix" someone adds to silence it.

★ Three loaders, three answersSELECT TRY_CAST('' AS INTEGER) AS try_cast, CAST(NULLIF('', '') AS INTEGER) AS nullif_cast, COALESCE(TRY_CAST('' AS INTEGER), 0) AS as_zero; -- try_cast NULL | nullif_cast NULL | as_zero 0
Silences the error and changes the averageCOALESCE(TRY_CAST(review_raw AS INTEGER), 0) AS review_score

The rule: an empty field that was NULL at source loads as NULL, using NULLIF(x, '') before the cast. If a column genuinely holds empty strings as values, say so in the runbook column by column; never set a blanket default.

Self-studyWhen the legacy engine has its own idea of empty2 min▶

Some engines merge the two concepts. Oracle's SQL reference says "The database currently treats a character value with a length of zero as null", and adds that this "may not continue to be true in future releases". If your legacy warehouse behaves that way and the new one does not, a filter like WHERE note IS NULL returns different rows on each side, with no error on either. Test it with a literal on both engines before you translate any filter on a text column, and record the answer in the runbook rather than in someone's memory.

Joins on nullable keys deserve the same care. Where a NULL key on both sides should match, the translation has to say so explicitly with IS NOT DISTINCT FROM; where it should not, leave = and write down why.

Real world

A vendor documents a behaviour and warns it may change. Oracle's own reference says its zero-length-string-as-null treatment "may not continue to be true in future releases". A translation rule that depends on an engine default is a rule with an expiry date nobody wrote down. Writing NULL handling explicitly in the SQL is how the rule survives the next upgrade of either engine.

Part 3 · covers time zones and case in comparisons

Time and text

5 min live

A fixed offset is right for most of the year and wrong for the rest. A key comparison that ignores case on one engine and respects it on the other leaves orders without a customer. Both pass every count you run.

LiveA named zone, not an offset3 min▶

The PostgreSQL documentation says a timestamptz is "stored internally as UTC, and the originally stated or assumed time zone is not retained", and that a timestamp without time zone "will silently ignore any time zone indication". DuckDB's says its TIMESTAMPTZ values "are displayed with the UTC offset of the configured time zone". So the instant is safe; the local day is computed at query time, by whatever rule the SQL text gives. Give it the zone's name, and the zone's history comes with it.

★ Summer and winter, both waysSELECT TIMESTAMPTZ '2017-01-15 02:30:00+00' AT TIME ZONE 'America/Sao_Paulo' AS named, TIMESTAMP '2017-01-15 02:30:00' - INTERVAL 3 HOUR AS fixed; -- named 2017-01-15 00:30:00 | fixed 2017-01-14 23:30:00 SELECT TIMESTAMPTZ '2017-07-10 02:30:00+00' AT TIME ZONE 'America/Sao_Paulo' AS named, TIMESTAMP '2017-07-10 02:30:00' - INTERVAL 3 HOUR AS fixed; -- named 2017-07-09 23:30:00 | fixed 2017-07-09 23:30:00

Named zones in DuckDB come from its ICU extension. In the build used for this page (1.5.3) it was already installed and loaded, and INSTALL icu; LOAD icu; ran cleanly. If your DuckDB rejects the zone name, run those two statements first.

LiveSame key, two spellings2 min▶

MySQL 8.0's default character set and collation, per its manual, mean "nonbinary string comparisons are case-insensitive by default". Many engines compare case-sensitively instead. If one of Serai's marketplace exports writes customer keys in lower case, a join that matched every order on a case-insensitive legacy engine leaves those orders without a customer on a case-sensitive new one. Nothing errors; a dimension just goes quiet.

★ Three ways to compareSELECT 'abc' = 'ABC' AS plain, lower('abc') = lower('ABC') AS lowered, 'abc' = 'ABC' COLLATE NOCASE AS nocase; -- plain false | lowered true | nocase true

The rule is a decision, not a default: state how keys are compared, and put it in the SQL. Normalising the key once at load (upper case, say) and comparing plainly afterwards keeps the rule in one place. A collation clause works in DuckDB too, as the output shows; whichever you choose, write it in runbook section 3 so every translated join follows it.

Self-studyWhy the fixed offset got written in the first place2 min▶

Hard-coding -03:00 for Brazil is not careless: for every date since Brazil stopped observing summer time it is correct, so every recent test passes. The error lives only in history, and only within an hour of midnight in the summer months. On Serai's sample those windows are 2016-10-16 to 2017-02-18 and 2017-10-15 to 2018-02-17. The bench's fixed-offset drift moves 72 orders placed between 00:00 and 00:59 civil time in those windows to the day before. Builder session 9 builds the edge check that catches it after cutover; tonight's job is to keep it out of the translation.

Real world

A time zone rule changed, and history did not. The IANA time zone database's 2019b release notes record that "Brazil no longer observes DST". Code written after that can treat Brazil as a fixed -03:00 and look right on every date it was tested on. A named zone carries the old rules for old dates; a fixed offset throws them away. The same reasoning holds for any country whose rules have changed.

Build-along

Five rules, each with its own test

★ 22 min · everyone builds

You need DuckDB: pip install duckdb and a Python prompt, or the DuckDB command-line shell. The setup loads a six-order export from Serai's legacy warehouse, as text where a file would carry text, plus a three-row customer table. Each step runs one rule's test: the wrong way and the rule's way in the same query. Every output below is what DuckDB 1.5.3 printed on this exact data.

Load the constructed export. Six orders as the legacy warehouse wrote them out: a UTC timestamp as text, review scores as text with one empty field, and two customer keys in lower case from the marketplace export that writes them that way. The session time zone is set to UTC so your local clock cannot leak into the results.

★ Setup (paste once)SET TimeZone = 'UTC'; CREATE OR REPLACE TABLE export_orders AS SELECT * FROM (VALUES ('o1','C1A7','2017-01-15 02:30:00',2,120.50,10.00,'5'), ('o2','B22F','2017-01-15 14:10:00',1, 59.90, 8.20,'4'), ('o3','c1a7','2017-01-16 01:45:00',1, 35.00, 7.10,''), ('o4','9E0D','2017-07-10 02:30:00',3,210.00,15.30,'3'), ('o5','b22f','2017-07-10 18:05:00',1, 44.00, 6.00,'5'), ('o6','9E0D','2017-07-11 12:00:00',1, 18.00, 4.40,'4') ) t(order_id, customer_key, placed_utc, items, item_value, freight, review_raw); CREATE OR REPLACE TABLE customers AS SELECT * FROM (VALUES ('C1A7'),('B22F'),('9E0D')) c(customer_key);

R1, division typed. // stands in for a legacy or target dialect whose / truncates. The rule casts first and rounds to four places at the end.

★ R1 · items per orderSELECT sum(items) / count(*) AS slash, sum(items) // count(*) AS truncated, round(CAST(sum(items) AS DECIMAL(12,4)) / count(*), 4) AS rule_r1 FROM export_orders; -- slash 1.5 | truncated 1 | rule_r1 1.5

R2, NULL kept NULL. The wrong way counts six reviewed orders and averages a zero in; the rule counts five and leaves the unreviewed order out of the average.

★ R2 · reviewed orders and average scoreSELECT count(COALESCE(TRY_CAST(review_raw AS INTEGER), 0)) AS reviewed_wrong, round(avg(COALESCE(TRY_CAST(review_raw AS INTEGER), 0)), 4) AS avg_wrong, count(CAST(NULLIF(review_raw, '') AS INTEGER)) AS reviewed_r2, round(avg(CAST(NULLIF(review_raw, '') AS INTEGER)), 4) AS avg_r2 FROM export_orders; -- reviewed_wrong 6 | avg_wrong 3.5 | reviewed_r2 5 | avg_r2 4.2

R3, time zone by name. One row per order, local day both ways. Only o1 disagrees: placed 00:30 local in summer time, pushed to the day before by the fixed offset. o3 is also in summer time but at 23:45 local, so both ways agree on its day.

★ R3 · local order daySELECT order_id, CAST(CAST(placed_utc AS TIMESTAMP) - INTERVAL 3 HOUR AS DATE) AS day_fixed, CAST(CAST(placed_utc || '+00' AS TIMESTAMPTZ) AT TIME ZONE 'America/Sao_Paulo' AS DATE) AS day_r3 FROM export_orders ORDER BY order_id; -- o1 | 2017-01-14 | 2017-01-15 -- o2 | 2017-01-15 | 2017-01-15 -- o3 | 2017-01-15 | 2017-01-15 -- o4 | 2017-07-09 | 2017-07-09 -- o5 | 2017-07-10 | 2017-07-10 -- o6 | 2017-07-11 | 2017-07-11

R4, keys compared by one stated rule. An exact join leaves the two lower-case keys unresolved; comparing in upper case resolves all six. The row count is six either way, which is why a count never sees this drift.

★ R4 · unresolved customer keysSELECT count(*) FILTER (WHERE c1.customer_key IS NULL) AS unresolved_exact, count(*) FILTER (WHERE c2.customer_key IS NULL) AS unresolved_r4 FROM export_orders o LEFT JOIN customers c1 ON c1.customer_key = o.customer_key LEFT JOIN customers c2 ON c2.customer_key = upper(o.customer_key); -- unresolved_exact 2 | unresolved_r4 0

R5, money as DECIMAL. Item value happens to come out the same both ways on these six rows; freight does not. A difference this small is harmless to a reader and fatal to an exact-equality check, which is why the bench signs it as accepted rather than pretending it away.

★ R5 · totals in DOUBLE and DECIMALSELECT sum(CAST(item_value AS DOUBLE)) AS value_double, sum(CAST(item_value AS DECIMAL(12,2))) AS value_r5, sum(CAST(freight AS DOUBLE)) AS freight_double, sum(CAST(freight AS DECIMAL(12,2))) AS freight_r5 FROM export_orders; -- value_double 487.4 | value_r5 487.40 | freight_double 50.99999999999999 | freight_r5 51.00

The test pack, runbook section 3. One query, one row per rule, the wrong way next to the rule's way. Keep it in the runbook beside the rules; Builder session 4 starts from the same export.

★ Runbook section 3 · test packSELECT 'R1 division typed' AS rule, CAST(sum(items) // count(*) AS VARCHAR) AS wrong_way, CAST(round(CAST(sum(items) AS DECIMAL(12,4)) / count(*), 4) AS VARCHAR) AS rule_way FROM export_orders UNION ALL SELECT 'R2 NULL kept NULL', CAST(round(avg(COALESCE(TRY_CAST(review_raw AS INTEGER), 0)), 4) AS VARCHAR), CAST(round(avg(CAST(NULLIF(review_raw, '') AS INTEGER)), 4) AS VARCHAR) FROM export_orders UNION ALL SELECT 'R3 zone by name', CAST(count(*) FILTER (WHERE CAST(CAST(placed_utc AS TIMESTAMP) - INTERVAL 3 HOUR AS DATE) = DATE '2017-01-15') AS VARCHAR), CAST(count(*) FILTER (WHERE CAST(CAST(placed_utc || '+00' AS TIMESTAMPTZ) AT TIME ZONE 'America/Sao_Paulo' AS DATE) = DATE '2017-01-15') AS VARCHAR) FROM export_orders UNION ALL SELECT 'R4 keys compared upper', CAST(count(*) FILTER (WHERE c1.customer_key IS NULL) AS VARCHAR), CAST(count(*) FILTER (WHERE c2.customer_key IS NULL) AS VARCHAR) FROM export_orders o LEFT JOIN customers c1 ON c1.customer_key = o.customer_key LEFT JOIN customers c2 ON c2.customer_key = upper(o.customer_key) UNION ALL SELECT 'R5 money as DECIMAL', CAST(sum(CAST(freight AS DOUBLE)) AS VARCHAR), CAST(sum(CAST(freight AS DECIMAL(12,2))) AS VARCHAR) FROM export_orders; -- R1 division typed | 1 | 1.5 -- R2 NULL kept NULL | 3.5 | 4.2 -- R3 zone by name | 2 | 3 -- R4 keys compared upper | 2 | 0 -- R5 money as DECIMAL | 50.99999999999999 | 51.00

A test that cannot fail proves nothing. Every row of the pack shows the wrong way producing a different number from the rule's way on this data. If you adapt the pack to your own estate and a rule's two columns agree, your sample does not contain the case the rule exists for: add a row that does before you trust the rule. Your numbers will differ.

Check yourself

Three questions

Clear all three and Builder session 3 gets stamped in your passport.

1 · Items per order is sum(items) / count(*) on both engines. The legacy engine prints 1.5; the new one prints 1. What happened?

Both operands are whole numbers. PostgreSQL documents that integer division "truncates the result towards zero"; DuckDB's / gives a floating-point answer. Cast to DECIMAL before dividing and the text says what you mean.

2 · The export writes a missing review score as an empty string, and the loader uses COALESCE(TRY_CAST(review_raw AS INTEGER), 0). What changes on the new side?

TRY_CAST gives NULL, and then COALESCE turns it into 0. Every unreviewed order now counts as reviewed with a score of 0. On the bench that is 8,546 reviewed orders becoming 8,614 and an average of 4.1390 becoming 4.1063.

3 · A report converts UTC to Brazilian local time with a fixed -03:00 offset. Every monthly number matches the legacy warehouse. Is the translation safe?

The instant is kept; the local day is wrong for orders between 00:00 and 00:59 in summer time. On the bench, 72 orders move a day, 74 daily numbers change and 0 monthly ones do. Translate with the zone's name.
