Part 1 · covers the timed end-to-end rehearsal

Time every step on a copy

5 min live

A plan says the final parity run takes two hours because someone guessed. A rehearsal says it took 105 minutes because someone watched. Run the whole day, in order, on a copy of production with the real volumes and the real people, and write down when each step started and finished.

LiveWhat a rehearsal is, and what it is not3 min▶

A rehearsal is the whole cutover day run end to end, in order, on a copy of production, by the people who will run it on the night, reading from the runbook rather than from memory. It is not a set of steps each tested on its own: the last delta load can pass alone and still overrun the slot the parity run needs, and only running them back to back shows that.

Serai rehearses the six steps of Leader session 5's timeline: freeze changes on legacy at 18:00, last delta load at 18:30, final rung-4 parity run at 20:00, go/no-go call at 22:00, switch readers at 22:15, announce at 22:45. Those planned hours are constructed, and so are the measured times on the figure; your own will differ, which is the point of measuring them. Each step gets a start and a finish in a log table, so the timings are data you can query, not a recollection in a chat thread.

Make the copy like the nightBecause
Same data volume as productionA delta load on a tenth of the rows times a tenth of the night

Same credentials and network pathA step that works from one engineer's laptop may fail from the on-call one

Self-studyReading the slack column2 min▶

Slack is the gap between a step finishing and the next step's planned start. On Serai's constructed rehearsal the final parity run took 105 minutes of its 120-minute slot, so the call at 22:00 has 15 minutes of margin. That is the number to watch. If a later rehearsal pushes the parity run past 22:00, the plan does not shorten the run: it moves the call later, because a go/no-go made while the report is still computing is a go made without gate 2.

The 1-minute switch has 29 minutes of slack before the announcement, and that time is not idle. It is when the first parity check runs against the readers' view on new, so the announcement goes out only after somebody has looked. Rehearse more than once if the timings move between runs; a step whose time varies a lot is a step to understand before the night.

Real world

A report of readiness is not a rehearsal. TSB's own release on the independent review of its 2018 migration says go-live "followed a long period of testing, with reports to the Board signalling readiness", and that the review raised "questions around how testing was carried out". What the review itself found is not quoted here. The lesson that carries is narrow and practical: a rehearsal log with start and finish times on every step is evidence someone can inspect, and a readiness report without it is a summary someone has to trust.

Part 2 · covers the rollback as a pointer swap

One pointer, two directions

5 min live

If readers query tables by name, switching them means editing every dashboard, extract and notebook, and switching back means editing them all again under pressure. Put one view between readers and the data. Cutover repoints the view to new; rollback repoints it to legacy. Same statement, opposite direction.

LiveReaders query a view, never a table3 min▶

In the weeks before cutover, every reader of a moving table is repointed from the table to a reporting view that, for now, still reads legacy. Nothing changes for the reader: same columns, same numbers. On the night, CREATE OR REPLACE VIEW reporting_orders AS ... FROM new_orders moves all of them at once, and the same statement with legacy_orders moves them all back. The build-along does exactly this and counts after every swap.

Add a column that says which side the view is serving, such as served_from. It costs nothing, and it means anyone looking at a number at midnight can tell which warehouse produced it, which is the same discipline as printing both targets on a parity report.

The view only helps if it really is the one name. Before the rehearsal, list every reader from the query log, the way Builder session 1 did, and check that none still names a table directly: a scheduled extract, a notebook, a dashboard built before the view existed. Each one is a reader the swap leaves behind.

LiveThree things that keep the swap reversible2 min▶
  1. Legacy keeps loading. The same loads run on both sides for the whole rollback window, so the warehouse you swap back to is current.
  2. Legacy is read-only for people. Loads write; nobody else does. A fix typed into legacy after the switch is a difference you did not prove.
  3. Nothing is written only to new. An analyst's new table or a corrected figure on the first morning is a write the way back loses. Log it or hold it until the window closes.

The window stays open until the written condition from Leader session 5 is met: the first month-end close on new has passed a rung-4 parity run and every monthly signer has said "same" or "explained". It is a condition, not a length; no source gives a right length, and Serai's 4-week parallel run before cutover is constructed.

Self-studyWhere the pointer is not a view2 min▶

Some readers cannot sit behind a view: a BI tool with its own extract, a cache that refreshes on a schedule, a partner who receives a file. For each one, write its own switch and its own way back in section 7, and time both in the rehearsal. A cached dashboard is the awkward case: after a rollback it may keep showing new's numbers until its next refresh. Force the refresh as part of the rollback step, and check it. Builder session 9 comes back to caches that outlive a cutover.

In engines where a view is bound to its table at creation, or where permissions sit on the view, check that the repointed view keeps its grants. Rehearse the swap with a reader's account, not an administrator's.

Real world

Gradual, validated, and reversible by design. Google's SRE book says "Almost all updates to Google's services proceed gradually, according to a defined process", and "If the change doesn't pass the validation period, it's automatically rolled back." The SRE Workbook defines canarying as "a partial and time-limited deployment of a change in a service and its evaluation", with the instruction to "pause and roll back the deployment" if it looks bad. That is one organisation's practice for services, not a rule for warehouses. The mechanism transfers: a view swap per wave is a partial change, the window after it is the validation period, and the rollback is cheap because it was built before the change.

Part 3 · covers the rollback trigger and rehearsing the way back

Make the rollback fire on the copy

5 min live

A rollback that has only ever been described is a hope. Rehearse it with the same stopwatch as the move, and rehearse the trigger too: plant a defect on the copy after the switch and confirm the check fires, the right person acts, and the numbers come back.

LiveThe trigger list, line by line3 min▶

Serai's trigger is the signed bar from Builder session 5 and Leader session 4, read again after every parity run on new once readers have moved, plus the edge check: orders exact; item value and freight within 0.05%; items per order within 0.005; reviewed orders exact; average review within 0.01; every one of the 595 near-midnight orders on the same day in both. Any line outside its band fires. One more line covers what a check cannot see: a reader reports a difference and nobody can explain it before the next scheduled run. All of it is constructed policy built from Serai's constructed bar, and it matches the trigger in Leader session 5 word for word, because there must be one trigger, not one per team.

The edge line earns its place. On the bench, the fixed-offset drift moves 72 orders to the day before and none crosses a month end, so the monthly bar shows 0 months failing: rung 3 misses it. Rung 4 adds the edge check and finds 72 of 595 near-midnight orders on another day. A trigger written from rung 3 would let that drift ride through cutover.

Print both targets on every trigger run. With both sides pointed at the new warehouse, the bench catches 0 of 5 defects and every check is green. A trigger check that compares new with new can never fire, so the first line of its output says what each side read. The build-along's trigger query does this in its compared column.

LiveRehearse the way back with the same stopwatch2 min▶

On the copy, after the switch: let the first morning's loads run on both sides, plant a defect on new (tonight, a late row appended twice), run the trigger check, watch it say "ROLL BACK", repoint the view to legacy, and count. Time the repoint and the count the same way as the forward steps, and write both into the rehearsal log. Leader session 5's gate 4 is met by exactly this record: readers moved to new and back on the copy, numbers checked after each move.

Then rehearse the awkward variants. Roll back from the on-call engineer's machine with their credentials. Roll back after a second load has run, so you know legacy is really current. Force the refresh of any cached reader and check its number. Each variant is a way the real rollback could fail at midnight that costs a few minutes to find on a Tuesday afternoon.

Self-studyWho pulls it, and what the builder does next2 min▶

The migration lead, one named person, pulls the trigger without asking first and tells the signers after; that is Leader session 5's rule and section 7 states it the same way. The builder's job is to make pulling it one statement the migration lead can run, or watch run, and to have the trigger query's output in front of them when they do.

After a rollback, readers are on numbers everyone trusts, so the cause is found calmly: which drift, which load, which step. The fix goes through the same suite, the nightly diff from Builder session 7 runs clean again, and the move waits for a new go/no-go. A rollback is not a failure of the migration; an unrehearsed one would be.

Real world

Integrity first, decided in the open. In GitHub's incident of 21 October 2018, connectivity was "restored in 43 seconds", yet one data centre's database "contained writes that were not present in the other data center". GitHub chose to "prioritize data integrity over site usability and time to recovery", and ran degraded for "24 hours and 11 minutes". At TSB, the Bank of England announced fines of "a total of £48,650,000" in 2022, finding the bank "failed to organise and control the IT migration programme adequately." Neither case sets your trigger. Both show the trade between the numbers and the clock gets made by someone; a rehearsed trigger makes it before the night, and keeps the way back a switch because no side took writes the other lacks.

Build-along

Swap forward, fire the trigger, swap back

★ 22 min · everyone builds

You need DuckDB: pip install duckdb and a Python prompt, or the DuckDB command-line shell. Constructed Serai Commerce example: ten orders on each side, a rehearsal log with the constructed timings from Part 1, and one reporting view. Every output below is what DuckDB 1.5.3 printed through its Python module on this exact data.

Set up both sides and the rehearsal log. Ten constructed orders on legacy, an identical copy on new (the state after the reload and the parallel run), and the six cutover steps with the constructed planned, started and finished times from Part 1.

★ Setup (paste once)CREATE OR REPLACE TABLE legacy_orders AS SELECT order_id, CAST(order_day AS DATE) AS order_day, CAST(item_value AS DECIMAL(12,2)) AS item_value FROM (VALUES (101,'2017-01-03',129.90),(102,'2017-01-03',54.50),(103,'2017-01-09',89.00), (104,'2017-01-17',210.40),(105,'2017-01-28',35.99),(106,'2017-02-02',149.00), (107,'2017-02-06',72.30),(108,'2017-02-14',18.90),(109,'2017-02-21',99.99), (110,'2017-02-27',64.00) ) o(order_id, order_day, item_value); CREATE OR REPLACE TABLE new_orders AS SELECT * FROM legacy_orders; CREATE OR REPLACE TABLE rehearsal_log AS SELECT step_no, step, CAST(planned AS TIME) AS planned, CAST(started AS TIME) AS started, CAST(finished AS TIME) AS finished FROM (VALUES (1,'freeze changes on legacy','18:00','18:00','18:10'), (2,'last delta load', '18:30','18:30','19:35'), (3,'final parity run, rung 4','20:00','20:00','21:45'), (4,'go/no-go call', '22:00','22:00','22:10'), (5,'switch readers', '22:15','22:15','22:16'), (6,'announce', '22:45','22:45','22:50') ) r(step_no, step, planned, started, finished);

Read the rehearsal. How long each step took, and how much room it left before the next step's planned start. lead() looks one row ahead; the last step has no next slot, so its slack is NULL.

★ Step time and slackSELECT step_no, step, date_diff('minute', started, finished) AS took_min, date_diff('minute', finished, lead(planned) OVER (ORDER BY step_no)) AS slack_min FROM rehearsal_log ORDER BY step_no; -- 1 freeze changes on legacy 10 | 20 -- 2 last delta load 65 | 25 -- 3 final parity run, rung 4 105 | 15 -- 4 go/no-go call 10 | 5 -- 5 switch readers 1 | 29 -- 6 announce 5 | NULL

Put readers on the view, still reading legacy. This happens weeks before the night. The served_from column says which side answered.

★ The reporting view, on legacyCREATE OR REPLACE VIEW reporting_orders AS SELECT 'legacy_orders' AS served_from, * FROM legacy_orders; SELECT served_from, count(*) AS orders, sum(item_value) AS item_value FROM reporting_orders GROUP BY served_from; -- legacy_orders | 10 | 923.98

Cutover: one statement. Every reader of the view now reads new. Same numbers, because new was proved level before the switch.

★ Swap forwardCREATE OR REPLACE VIEW reporting_orders AS SELECT 'new_orders' AS served_from, * FROM new_orders; SELECT served_from, count(*) AS orders, sum(item_value) AS item_value FROM reporting_orders GROUP BY served_from; -- new_orders | 10 | 923.98

The first morning's loads, with a planted defect. Both sides receive order 111. New also receives order 105 again from the late feed, appended rather than merged: the same mechanism that put 367 duplicated keys on the bench. Readers now see 12 orders.

★ Morning load (both sides keep loading)INSERT INTO legacy_orders VALUES (111, DATE '2017-02-28', 45.00); INSERT INTO new_orders VALUES (111, DATE '2017-02-28', 45.00); INSERT INTO new_orders VALUES (105, DATE '2017-01-28', 35.99); SELECT served_from, count(*) AS orders, sum(item_value) AS item_value FROM reporting_orders GROUP BY served_from; -- new_orders | 12 | 1004.97

The trigger check. Two lines of the signed bar at the monthly grain: orders exact, item value within 0.05%. The first column prints both targets, so this check cannot quietly compare new with new. January fails on both lines.

★ Trigger: the signed bar after the switchWITH l AS ( SELECT strftime(order_day, '%Y-%m') AS month, count(*) AS orders, sum(item_value) AS item_value FROM legacy_orders GROUP BY month ), n AS ( SELECT strftime(order_day, '%Y-%m') AS month, count(*) AS orders, sum(item_value) AS item_value FROM new_orders GROUP BY month ) SELECT 'legacy_orders vs new_orders' AS compared, coalesce(l.month, n.month) AS month, l.orders AS legacy_n, n.orders AS new_n, round(100 * abs(n.item_value - l.item_value) / l.item_value, 3) AS value_gap_pct, CASE WHEN l.orders IS DISTINCT FROM n.orders OR abs(n.item_value - l.item_value) > 0.0005 * l.item_value THEN 'ROLL BACK' ELSE 'within bar' END AS verdict FROM l FULL OUTER JOIN n ON l.month = n.month ORDER BY month; -- legacy_orders vs new_orders | 2017-01 | 5 | 6 | 6.924 | ROLL BACK -- legacy_orders vs new_orders | 2017-02 | 6 | 6 | 0.0 | within bar

Rollback: the same statement, pointed back. Readers see legacy again, and legacy is current: 11 orders, including the morning's order 111, and order 105 once.

★ Swap backCREATE OR REPLACE VIEW reporting_orders AS SELECT 'legacy_orders' AS served_from, * FROM legacy_orders; SELECT served_from, count(*) AS orders, sum(item_value) AS item_value FROM reporting_orders GROUP BY served_from; -- legacy_orders | 11 | 968.98
A rollback that is really a second migration -- rollback: if numbers look wrong after cutover, stop the loads into legacy, -- then reload legacy from new and repoint each dashboard by hand.

Note what the IS DISTINCT FROM is for. If a month exists on only one side, the FULL OUTER JOIN gives NULL for the other side's count, and l.orders <> n.orders would be NULL, which a CASE treats as not true: the month would read "within bar". IS DISTINCT FROM treats NULL as a comparable value, so a missing month fires the trigger. Builder session 3 showed the same three-valued logic breaking a translation.

Check yourself

Three questions

Clear all three and Builder session 8 gets stamped in your passport.

1 · What makes Serai's rollback a single statement rather than a second migration?

The view makes the switch one pointer; the loads make the target of that pointer current. Without either, the way back is editing every reader or reloading legacy. D states a length no source gives: Serai's 4-week parallel run is constructed, and the window ends on a written condition.

2 · After the switch, the trigger query prints "2017-01 · 5 · 6 · ROLL BACK". What happens next?

The decision was made when the trigger was written. A and B reopen it on the night; C is a write on one side only, a fix nobody has proved, and it leaves the late feed that caused it still running.

3 · The rehearsal shows the final parity run took 105 minutes of a 120-minute slot. A later rehearsal takes 140. What changes in the plan?

Gate 2 reads a complete rung-4 report. B makes the call without it; C turns rung 4 into rung 3, which misses the fixed-offset drift (0 months fail at the monthly grain); D throws away the only measured hours you have.
