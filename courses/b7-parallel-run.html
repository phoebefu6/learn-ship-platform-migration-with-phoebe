Part 1 · covers running legacy and new side by side

Two systems, one truth

5 min live

A parallel run is not two warehouses that both happen to be on. It is one set of feeds loaded into both, one set of readers on legacy, and one comparison every night that decides, slowly and in writing, whether the new side has earned the readers.

LiveWhat "parallel" means, and what it does not3 min▶

Four rules turn two running warehouses into a parallel run you can learn from.

  • One set of feeds. Every source lands in both sides from the same extract, with the same cutoff. If the new side reads its own copy of an export, a difference may be the copy, not the migration.
  • One system of record. Legacy stays the answer until cutover. Every dashboard, report and analyst reads legacy. Nobody quotes a number from the new side, however good it looks.
  • Nothing written to one side only. A fix to a job is made in the migration code and both sides reload. A hand patch on the new side makes the next night's diff meaningless.
  • One reader on the new side: the diff. Its output is the only evidence the run produces, so it is stored, not glanced at.
Self-studySame inputs, or the diff measures your schedule3 min▶

On 31 October, constructed, Serai's new nightly load started before the late feed had landed, and legacy's started after it. Counts and monthly parity both failed that night, with nothing wrong in the translated SQL. The diff was comparing two different moments.

The fix is a cutoff both sides share: each night records which feed files, or which load id, it consumed, and the diff refuses to run until both sides report the same one. That turns a timing gap into a skipped night with a reason, rather than a false failure. Re-running a night after a fix must also give the same answer twice; that is idempotency, which Data Reliability Builder 5 owns. The parallel run only asks for it.

Real world

Vendors describe the overlap as a feature. A 2019 Google Cloud blog on moving data warehouses describes an iterative move in which "both your data warehouse and BigQuery can be actively used in parallel". Read it as a vendor claim about its own process. It is also an honest description of the cost: actively used in parallel means actively loaded, run and paid for in parallel. The leader track's session 6 closes that cost case; this session only makes sure the overlap buys evidence.

Part 2 · covers the rung-4 suite every night, stored as rows

The nightly diff

5 min live

Every night the full suite runs against both sides: counts, keys, monthly parity against the signed bar, and the time-zone edge check. Its output is one row per check per night, so a month of nights is a grid you can read at a glance and a table you can query.

LiveOne row per check per night3 min▶

The diff writes a narrow table, not a report. Narrow means a new check is a new value in a column, not a new column, and a missing check is a missing row you can count.

ColumnWhy it is there
nightThe load the check ran against, not the time the job happened to finish
check_namecounts, keys, parity, edge: the rung-4 suite from sessions 4, 5 and 9
statuspass or fail against the signed bar, decided by the check, not by the reader
detailThe number that failed, in the bench's words, so the morning reader can start without rerunning anything

On the bench, this suite with the signed bar catches 5 of 5 planted defects with 0 false alarms. That is why a red cell is worth a person's morning: it is not the floating-point noise or the per-line rounding Serai agreed to accept. In a real estate, add two columns the bench taught at its break button: the connection target each side read. A report that cannot say what it compared proves nothing.

Self-studyWhere the daily exact view fits2 min▶

Session 5 kept the daily exact comparison as a read-only view. It flags both accepted differences, so on the bench it raises 2 false alarms, and counting it in "clean" would mean no night is ever clean. It stays out of nightly_diff's verdict and in a person's morning read, because it is the view most likely to surface a drift nobody planned for. If a person finds one there, it becomes an open item, and open items are part of the exit rule in Part 3.

Alerting on a red row, paging someone, deciding who looks first: that is monitor design, and Data Observability owns it. This session owns what is compared and what the comparison must say.

Real world

Tools report; people decide what blocks. AWS's Database Migration Service documentation says its validation "compares each row in the source with its corresponding row at the target, verifies the rows contain the same data, and reports any mismatches". Google's open-source Data Validation Tool offers column, row, schema and custom-query validation. Both are vendor claims, and both stop at the report. Neither knows which mismatches Serai signed as accepted, nor whether a night with a missing check counts. Those rules live in the runbook, which is why the diff's output has to be a table the runbook's rules can be run against.

Part 3 · covers exit criteria and the cost of running two

A written rule for stopping

5 min live

How long a parallel run should last is contested, and no source gives a number. What is not contested is that the end is a rule written before the run starts, with an owner, and that the rule can say "not yet" on the day the plan said "done".

LiveSerai's exit rule, in one sentence3 min▶

Serai's rule, a constructed policy written before the first night: the rung-4 suite clean on 14 consecutive nights, where a night is clean only when all four checks ran and passed, and every item on the open-items list closed; the migration lead signs it.

Each clause closes a door. "Consecutive" means a bad night resets the count, so a run cannot reach its number by averaging. "All four ran" means silence is not a pass. "Every item closed" covers what the suite cannot see: a reader's complaint, a drift a person spotted in the daily view, a job that failed without alerting. "Signs it" means one named person, not a meeting.

Why 14 and not some other number? No source gives one. Serai's 4 weeks is 28 nights, so the rule asks for at least the second half of the plan to be clean in a row; a business with a weekly or month-end peak might want the streak to include one. Leader session 6's 30-night watch is a different window: it starts after cutover, with readers already on the new side.

Self-studyThe cost of running two, and why it does not shorten the rule2 min▶

Every night of the run is paid twice: two loads, two warehouses, and the people who read the diff and chase its red cells. That pressure is real, and it arrives at exactly the moment the rule says "not yet". It is the reason the rule is written before the run, when nobody is tired of it yet.

The honest trade is not shorter against longer. It is what a missed defect costs once readers have moved, against what one more week of two systems costs. Serai's constructed answer on 15 November: five more clean nights, the open item closed, and the earliest exit is 20 November. No real prices here; the leader track's session 6 treats the cost case as a shape, not a number.

Real world

Readiness reported is not readiness defined. TSB's own release on the review of its 2018 migration says go-live "followed a long period of testing, with reports to the Board signalling readiness", and that the review raised "questions around how testing was carried out". In 2022 the Bank of England fined TSB "a total of £48,650,000" and said it "failed to organise and control the IT migration programme adequately". One case is not a base rate, and the review itself is not quoted here. The contrast with Google's SRE book is useful: there a change that "doesn't pass the validation period" is "automatically rolled back". A validation period with a written pass condition is what an exit rule is.

Build-along

Are we clean, and since when?

★ 22 min · everyone builds

You need DuckDB: pip install duckdb and a Python prompt, or the DuckDB command-line shell. Paste the setup once, then run the queries in order. The data is a Constructed Serai Commerce example: four weeks of nightly results and an open-items list. Every output below is what DuckDB printed on exactly this setup.

Load the constructed run. Twenty-eight nights from 19 October to 15 November 2026, four checks a night, every result a pass unless the failures list says otherwise. Then one row is deleted, because on 6 November the parity job on the new side never ran. The failure details are the bench's own numbers for the late-rows drift.

★ Setup (paste once)CREATE OR REPLACE TABLE nightly_diff AS SELECT CAST(n.night AS DATE) AS night, c.check_name, coalesce(f.status, 'pass') AS status, coalesce(f.detail, '') AS detail FROM generate_series(DATE '2026-10-19', DATE '2026-11-15', INTERVAL 1 DAY) n(night) CROSS JOIN (VALUES ('counts'), ('keys'), ('parity'), ('edge')) c(check_name) LEFT JOIN (VALUES (DATE '2026-10-19', 'counts', 'fail', 'rows 8,614 vs 8,981'), (DATE '2026-10-19', 'keys', 'fail', '367 duplicated keys on new'), (DATE '2026-10-19', 'parity', 'fail', 'orders fail all 21 months'), (DATE '2026-10-20', 'counts', 'fail', 'rows 8,614 vs 8,981'), (DATE '2026-10-20', 'keys', 'fail', '367 duplicated keys on new'), (DATE '2026-10-20', 'parity', 'fail', 'orders fail all 21 months'), (DATE '2026-10-31', 'counts', 'fail', 'new loaded before the late feed'), (DATE '2026-10-31', 'parity', 'fail', 'new loaded before the late feed') ) f(night, check_name, status, detail) ON f.night = CAST(n.night AS DATE) AND f.check_name = c.check_name; -- the parity job on new did not run on 6 November: no row at all DELETE FROM nightly_diff WHERE night = DATE '2026-11-06' AND check_name = 'parity'; CREATE OR REPLACE TABLE open_items AS SELECT * FROM (VALUES (1, DATE '2026-10-19', 'late rows appended on new: load must merge on key', 'closed'), (2, DATE '2026-10-31', 'new nightly load ran before the late feed landed', 'closed'), (3, DATE '2026-11-06', 'parity job on new did not run, and nothing alerted', 'open') ) t(item, raised, what, state);

Q1, the shape. Before any verdict, count what is there. 28 nights times 4 checks is 112, and the table holds 111. That one-row gap is the whole lesson of Q5.

★ Q1 · rows, nights, failuresSELECT count(*) AS check_rows, count(DISTINCT night) AS nights, count(*) FILTER (WHERE status = 'fail') AS failing_rows FROM nightly_diff; -- check_rows 111 | nights 28 | failing_rows 8

Q2, the diff dashboard. Pivot the last two weeks into the grid from Part 2: one row per night, one column per check. The missing run shows as NULL, not as a failure, which is exactly how it slips past a careless reader.

★ Q2 · nights by checksPIVOT (SELECT night, check_name, status FROM nightly_diff WHERE night >= DATE '2026-11-03') ON check_name IN ('counts', 'keys', 'parity', 'edge') USING first(status) ORDER BY night; -- 13 rows; every cell pass except -- 2026-11-06 | pass | pass | NULL | pass

Q3, the unclean nights and why. A night is clean only when 4 checks ran and all 4 passed. Four nights are not, and 6 November is unclean with nothing failed at all.

★ Q3 · what went wrong, by nightSELECT night, count(*) AS checks_run, count(*) FILTER (WHERE status = 'pass') AS checks_passed, string_agg(check_name || ': ' || detail, '; ' ORDER BY check_name) FILTER (WHERE status = 'fail') AS failed FROM nightly_diff GROUP BY night HAVING NOT (count(*) = 4 AND bool_and(status = 'pass')) ORDER BY night; -- 2026-10-19 | 4 | 1 | counts: rows 8,614 vs 8,981; keys: 367 duplicated keys on new; parity: orders fail all 21 months -- 2026-10-20 | 4 | 1 | counts: rows 8,614 vs 8,981; keys: 367 duplicated keys on new; parity: orders fail all 21 months -- 2026-10-31 | 4 | 2 | counts: new loaded before the late feed; parity: new loaded before the late feed -- 2026-11-06 | 3 | 3 | NULL

Q4, are we clean, and since when? Find the last unclean night; every night after it is the current streak. This is the number the exit rule reads.

★ Q4 · the clean streakWITH per_night AS ( SELECT night, count(*) = 4 AND bool_and(status = 'pass') AS clean FROM nightly_diff GROUP BY night ) SELECT min(night) AS clean_since, max(night) AS last_night, count(*) AS clean_nights FROM per_night WHERE night > (SELECT max(night) FROM per_night WHERE NOT clean); -- clean_since 2026-11-07 | last_night 2026-11-15 | clean_nights 9

Q5, the version that looks right. Drop the count(*) = 4 test and ask only whether every row that exists passed. The night with a missing check now counts as clean, the streak grows to 15, and a 14-night rule would let Serai exit on a check that never ran.

Looks right, reads a missing check as a passWITH per_night AS ( SELECT night, bool_and(status = 'pass') AS clean FROM nightly_diff GROUP BY night ) SELECT min(night) AS clean_since, max(night) AS last_night, count(*) AS clean_nights FROM per_night WHERE night > (SELECT max(night) FROM per_night WHERE NOT clean); -- clean_since 2026-11-01 | last_night 2026-11-15 | clean_nights 15

Q6, the exit verdict. Runbook section 6 in one query: the streak against 14, the open items against 0, and the earliest date the rule could be met if every night from here is clean.

★ Q6 · runbook section 6, the exit ruleWITH per_night AS ( SELECT night, count(*) = 4 AND bool_and(status = 'pass') AS clean FROM nightly_diff GROUP BY night ), streak AS ( SELECT count(*) AS clean_nights FROM per_night WHERE night > (SELECT max(night) FROM per_night WHERE NOT clean) ), items AS ( SELECT count(*) FILTER (WHERE state = 'open') AS open_items FROM open_items ) SELECT s.clean_nights, i.open_items, s.clean_nights >= 14 AND i.open_items = 0 AS exit_rule_met, CAST(DATE '2026-11-15' + INTERVAL (14 - s.clean_nights) DAY AS DATE) AS earliest_exit_if_clean FROM streak s, items i; -- clean_nights 9 | open_items 1 | exit_rule_met false | earliest_exit_if_clean 2026-11-20

Why Q4 needs a night to exist at all. Q4 counts nights that have at least one row. If a whole night's suite failed to run, that night has no rows and vanishes from per_night, and the streak skips over it. The fix is the move from Builder session 1: start from the list of expected nights, here generate_series over the run's dates, and LEFT JOIN the results to it. Homework item 3 asks you to make that change.

Homework

Three questions

Clear all three and Builder session 7 gets stamped in your passport.

1 · On 15 November, Q5 says 15 clean nights since 1 November and Q4 says 9 since 7 November. Which is right, and why?

bool_and over the rows that exist cannot see a row that does not. Requiring all four checks per night turns silence into an unclean night, which is the only safe reading.

2 · The new warehouse's numbers have matched for a week. An analyst wants to point a dashboard at it now. What does the parallel run say?

A reader on the new side before cutover is a cutover nobody rehearsed, with no rollback plan, for one dashboard. Session 8 moves readers deliberately, all at once, with a way back.

3 · The planned four weeks end on 15 November and the exit rule is not met. What happens next?

Four weeks is a constructed plan and no source gives a length. The rule was written before the run so that it could say "not yet" at the moment everyone wants to hear "done".
